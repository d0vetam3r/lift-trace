# OBS 네이티브 렌더링 주기 실험

[한국어](README.ko.md) · [日本語](README.ja.md) · [English](README.md)

이 코드는 선택적으로 사용하는 렌더링 실험이며, **정식 배포된 대체 오버레이가 아닙니다**.
OBS가 영상을 합성할 때 입력 노트를 직접 그리면 브라우저 소스에서 관측된
동일 프레임 반복과 뒤늦은 이동 현상이 줄어드는지 확인합니다.
이 파일들은 기존 Lift Trace 실행 파일, 설정 UI, 실제 입력 기록,
오버레이 자동 제어, Live Core, Remote를 변경하지 않습니다.
Lift Trace의 독립 실행, 시작부터 최대 4분까지 저장하는 규칙,
다음 판 시작 시 미저장 영상을 폐기하는 규칙도 유지됩니다.
이 시험용 모듈은 일반 앱 배포에 포함되지 않습니다.

녹화 비교 결과와 검증 범위는 [측정 결과](RESULTS.md)를 참고하세요.

## 실제 입력과 기존 설정 UI 연결 (Windows)

시험용 실행기는 기존 `Bridge.subscribe()` 입력 스트림을 구독합니다.
별도로 실행한 Node 프로세스에서 수정하지 않은 `web/client.js`의 `InputClient`,
`TrailEngine`, `ScratchTracker`를 그대로 사용합니다. 기존 UI의 컨트롤러 선택,
버튼 매핑, 스크래치 축·방향 반전·감도·정지 유예, 설정 변경과 초기화를 함께 받습니다.
원래 입력 기록에 변경 내용을 되돌려 쓰지 않습니다.

```text
python experiments/obs-native-pacing/live_launcher.py --node PATH_TO_NODE_EXE --channel lift-test
```

이 실험에는 Python 3.10+, Node 22+, 별도로 빌드한 플러그인이 필요합니다.
일반 Lift Trace는 Node·플러그인·Live Core·Remote 없이 계속 독립 실행됩니다.
기존 설정 UI를 `http://127.0.0.1:8766/`에서 제공하고, 기본 설정 저장 위치는
격리된 `artifacts/native-live-data`입니다. 여기서 컨트롤러를 선택하고 기존 조절
항목을 사용합니다. 기존 UI의 설정 가져오기로 복사한 설정을 읽을 수 있으며,
C 렌더러 전용 설정 파일을 따로 관리하지 않습니다. 두 실행기가 같은 설정 폴더를
동시에 쓰게 하지 마세요. OBS 시험 소스의 `Live channel`에는 같은 `lift-test`를 넣습니다.
연결 작업은 별도 스레드가 맡고, 아직 실행되지 않은 상대를 100ms마다 다시 찾으므로
어느 쪽을 먼저 실행해도 됩니다. 실시간 모드의 진단 영역은 기본 꺼짐입니다.

Windows 세션 내부의 공유 메모리로 최대 4,096개 입력 구간을 전달합니다.
OBS는 잠금을 기다리지 않고 스냅샷을 읽어 자체 프레임 시계로 그립니다.
연결이 멈추거나 잘못된 데이터가 오면 1초 이내에 입력 노트를 지웁니다.
기존 입력 폴링과 UI는 계속 동작합니다. 관찰자는 스크래치 정지를 4ms 간격으로
확인하므로 60Hz 브라우저보다 유예 종료를 약 한 프레임 먼저 관찰할 수 있습니다.
실제 샘플의 시각과 기존 스크래치 유예 정책은 유지합니다.

건반 머리/몸통, 짧은 입력 표시 비율, 지연, 1P/2P, 크기, 속도, 가이드와 배경은
기존 UI 설정을 따릅니다. 스크래치는 건반 표시 옵션과 관계없이 몸통과 방향별
색상·화살표를 유지합니다. 선택적인 자동 배치·표시 연결은 아래에서 설명합니다.
실행기가 기존 소스나 녹화 대상을 자동 이전하지는 않습니다. 실제 플레이와 입력 지연은 별도 확인이 필요하며,
자동 입력 시험을 실물 컨트롤러 검증으로 해석하지 마세요.

소스는 `lift_trace_native_pacing`이라는 OBS 소스를 등록합니다.
시험할 OBS와 일치하는 공식 OBS SDK의 `obs-module.h`, `util/platform.h`,
libobs를 사용해 별도 플러그인으로 빌드합니다. C11 원자 연산을 사용하며,
C++은 필요하지 않으며 Windows 연결 작업은 작은 별도 스레드에서 수행합니다.
연결 핸들을 여는 작업은 OBS 영상 스레드에서 하지 않습니다.
별도 프로필과 장면을 갖춘 일회용 OBS 설치본에서만 로드하세요.
시험용 DLL을 평소 사용하는 OBS 설치 폴더나 릴리스 패키지에 복사하지 마세요.
저장소에는 OBS 헤더·라이브러리·컴파일된 바이너리를 포함하지 않습니다.
`CMakeLists.txt`는 공식 SDK를 사용할 때 참고하는 빌드 경로이며,
이번 환경에서 실행해 검증하지 않았습니다. 실제 녹화 실험에서는 Clang과
로컬의 최소 ABI 헤더를 사용했습니다. 해당 헤더와 로컬 도구 체인은
이 실험의 공개 소스에 포함되지 않습니다.

## 구현 범위

### 이미 실행 중인 Lift Trace 앱에 연결

기존 앱이 입력 서버를 실행하고 있다면 `live_launcher.py`를 추가 실행하는 대신
`live_observer.py --node PATH_TO_NODE_EXE --channel lift-test --port 8765`를
사용합니다. 이 선택적 전달 프로세스는 기존 로컬 상태·이벤트 스트림만 읽습니다.
입력 폴링·UI·자동 표시·녹화 서비스를 중복 실행하거나 앱 설정을 쓰지 않습니다.
연결이 끊기거나 잘못된 스트림을 받으면 스냅샷을 무효화하고 자신이 시작한 Node를
종료한 뒤, 새 엔진으로 서버의 현재 상태를 받아 다시 연결합니다.

OBS와 함께 실행하려면 `obs-native-observer.lua`를 추가하고 Python·Node 경로,
기존 Lift Trace 포트와 채널을 지정한 뒤 선택적 자동 실행을 켭니다.
관리자 권한을 요청하지 않고 숨김으로 실행하며, OBS의 정확한 생성 시각을 확인합니다.
해당 OBS가 종료되면 전달 프로세스와 자식 프로세스도 종료됩니다. 기존 앱·도우미는
자신의 서버와 자동 표시를 계속 관리합니다. Lift Trace나 리모컨의 포트에서 서버를
중복 실행하지 마세요. 선택적 상태 JSON은 연결·수명 정보만 담고 실제 입력·설정은
담지 않습니다. 스크립트 제거·재로드 시 추측한 PID로 다른 프로세스를 종료하지 않으며,
처음 연결한 OBS의 수명을 따릅니다.

### 선택적인 OBS 자동 배치와 자동 표시

격리된 OBS에 `obs-native-layout.lua`를 스크립트로 추가합니다. 실행기와 같은
실시간 채널과 별도의 소스 이름을 지정하고, 배치할 장면에서 추가·연결 버튼을
사용합니다. 새 항목은 숨김 상태로 만들고, 기존 항목의 표시 상태는 유지합니다.
버튼은 표준 배치를 위해 배율·자르기·회전·정렬·경계 설정을 초기화합니다.
그 뒤 설정 추종은 X/Y 위치만 바꾸며 표시 상태·순서·잠금·나머지 변환을 유지합니다.
위치를 수동으로 관리하려면 추종을 끕니다.

기존 설정 UI의 1P/2P, LIFT, `obsOffsetX/Y`를 사용하고, `getObsPlacement`와 같은
1920×1080 기준으로 계산합니다. 출력 크기는 기존 렌더러 설정을 따릅니다.
배치 타이머는 공유 메모리의 작은 헤더만 잠금 대기 없이 읽으며, 파일 읽기·소켓 요청·
핸들 열기를 반복하지 않습니다. 데이터가 없거나 오래되었거나 잘못되면 마지막 위치를
유지합니다. 실행 순서는 관계없으며 같은 채널의 전달 프로세스를 다시 실행해도
장면 항목의 표시 상태를 바꾸지 않습니다.

장면 UUID·항목 ID·소스 UUID·채널을 고정하여 저장합니다. 이름을 바꿔도 연결을 유지하고,
장면을 전환해도 다른 항목을 따라가지 않습니다. 소스·항목을 교체하거나 채널을 바꾸면
명시적으로 다시 연결해야 합니다. 중복 배치는 이미 고정된 정확한 항목이 있을 때만
허용하며, 같은 이름의 브라우저 소스를 교체하지 않습니다. 배치 보정값을 전달하는
프로토콜 v2를 사용하므로 실행기와 함께 시험 플러그인도 다시 빌드해야 합니다.
v1 데이터는 이전 예약 공간을 위치 값으로 오인하지 않도록 거부합니다.

자동 표시는 실행기의 **기존 자동 제어 UI**에서 격리된 OBS에 연결하고 게임 캡처와
C 오버레이 항목을 선택·저장한 뒤 시작합니다. 기존 감지·지연 확정·캡처 복구 정책을
그대로 사용합니다. 배치 기능이 자동 표시를 시작하거나 기존 항목을 켜고 끄지는 않습니다.
소스 실행에서 자동 표시를 사용할 때 필요한 선택 의존성은
[개발 가이드](../../docs/DEVELOPMENT.md)에 있습니다.

Live Core는 선택적 연동이며 수정하지 않았습니다. 나중에 녹화까지 이전할 때는
Core에서도 새 C 항목의 식별자를 명시적으로 선택해야 합니다. 소스 생성·이름 변경만으로
기존 녹화 대상을 바꾸지 않습니다. 최초 최대 240초 보관과 다음 판의 미저장 영상 폐기는
Core에서 유지합니다. 이번 변경은 실제 방송 환경에 설치하거나 설정을 변경하지 않습니다.

- 실시간 채널을 비우면 합성 건반 입력을 그립니다. 인덱스 -3부터 120ms마다 누르고,
  `positiveMod(index, 7) + 1` 레인에서 40ms 동안 유지합니다.
  이 비교 모드는 컨트롤러를 읽지 않습니다. 실시간 연결은 위의 선택적 관찰자를 사용합니다.
- 기존 정규화된 설정을 `lift_settings`라는 OBS 데이터 객체로 전달할 수 있습니다.
  시험 도구가 전달하는 설정 스냅샷이며, 별도로 관리하는 사용자 설정 파일이 아닙니다.
  실시간 모드는 기존 UI 스트림에서 정규화된 설정을 받습니다.
- `video_tick`에서 OBS 영상 프레임의 시각과 설정 스냅샷을 가져옵니다.
  별도로 실행되는 브라우저 애니메이션 시계 대신 이 스냅샷으로 그립니다.
  설정 변경은 짧은 잠금으로 보호하며 파일·파이프 입출력과 그래픽 API는 밖에서 처리합니다.
  공유 메모리 잠금은 기다리지 않습니다. 합성 시계가 0이거나 뒤로 이동해도 경과 시간이
  음수가 되지 않도록 처리합니다.
- 레인 비율, 이동 속도 계산, 표시 지연, 머리만 표시하거나 몸통을 함께 표시하는 옵션,
  종료된 짧은 입력의 표시 규칙은 기존 계산을 따릅니다.
  시각적 옵션으로 입력 타임스탬프를 바꾸지 않습니다.
  속도를 매우 낮게 설정해도 브라우저 엔진과 같은 4,096개 이벤트 한도로
  처리량을 제한합니다.
- 위치·크기·시간 계산의 일치를 확인하는 실험입니다.
  Canvas의 가장자리 안티앨리어싱, 색상 처리, 스크래치 표시,
  모든 OBS 모드에서의 투명도가 완전히 같다고 보장하지 않습니다.

기본값은 입력 노트 영역 432 × 290px, 그 아래 진단 영역 100px,
머리 두께 12px, 속도 849.9266666666666px/s입니다.
합성 비교 모드에서는 7개 건반 레인을 사용하고 스크래치는 레인 폭만 확보합니다.
동일한 조건으로 비교하려면 432 × 390, 60fps, 크기 조정 없음,
불투명 배경을 사용하세요. 진단 바코드에는 최소 336px 폭이 필요합니다.
그 외 정규화된 폭은 이번 렌더링 주기 비교의 검증 범위에 포함하지 않습니다.

## 진단 값과 해석

24비트 행 5개를 사용하며 각 셀은 10 × 14px입니다.
`x = 8 + bit * 12` 위치에 최하위 비트부터 배치합니다.
기본 높이에서 각 행의 위쪽 좌표는 300, 318, 336, 354, 372입니다.
각 행의 x=308과 x=324에는 흰색·검은색 보정 사각형을 배치합니다.

| 행 | 네이티브 렌더러 값 |
| --- | --- |
| 1 | OBS 영상 tick 순번 |
| 2 | OBS 애니메이션 경과 시간, 0.1ms 단위 |
| 3 | tick 콜백의 OS 경과 시간, 0.1ms 단위 |
| 4 | 합성 모드: 2행과 동일. 실시간 모드: UTC 애니메이션 ms × 10을 24비트로 순환 |
| 5 | 이전 렌더 콜백의 CPU 실행 시간, µs 단위 |

2행은 초기화된 첫 OBS 영상 tick에서, 3행은 첫 콜백에서 0으로 시작합니다.
이번 시험에서 기대하는 것처럼 첫 tick에 유효한 OBS 시각이 제공되면
두 값의 시작점이 일치합니다. 처음 OBS 시각이 0이면 2행의 시작점이 늦어질 수
있으므로, 두 값의 차이는 절대적인 시계 위상 차이를 측정한 값이 아닙니다.
렌더 실행 시간에는 GPU 작업 완료와 영상 인코딩이 포함되지 않습니다.
하나의 tick을 여러 렌더 호출에서 사용하는 것은 정상일 수 있으므로,
카운터와 함께 별도로 측정한 픽셀 이동 및 출력 PTS도 확인해야 합니다.
작은 합성 비교에서 통과했다는 사실만으로 실제 플레이 동작이나
OBS/GPU 과부하 상황에서의 안정성까지 입증되지는 않습니다.

## 위치·크기 계산 회귀 검사

`geometry-test.c`를 별도 공유 라이브러리로 빌드합니다.
OBS에 의존하지 않으며 `pacing_geometry_tests`와 `pacing_geometry_sample`을
내보냅니다. 다음과 같이 실행합니다.

```text
python check-geometry.py path/to/geometry-test.dll --node path/to/node
```

시계 시작·역행, 처리량 제한, 실제 `web/engine.js`와 `web/render.js` 코드를
호출해 생성한 420개 비교 벡터를 검사합니다.
머리만 표시하거나 몸통을 함께 표시하는 경우, 짧은 입력의 표시 비율과
엄격한 기준 시간 경계, 표시 지연, 1P/2P 배치,
누르기 전·유지 중·놓은 뒤·정리된 상태 및 원래 타임스탬프 보존을 확인합니다.
검사는 OBS 프로세스를 실행하거나 개인 설정에 접근하지 않습니다.
