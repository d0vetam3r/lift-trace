# OBS ネイティブ描画のフレーム周期実験

[한국어](README.ko.md) · [日本語](README.ja.md) · [English](README.md)

これは合成入力を使う描画実験であり、**実際のプレイ用オーバーレイを置き換える製品ではありません**。
OBS が映像を合成する際に入力ノーツを直接描くことで、ブラウザーソースで
観測された同一フレームの繰り返しと、その後の急な移動を避けられるか確認します。
これらのファイルは、既存の Lift Trace 実行ファイル、設定 UI、実入力の記録、
オーバーレイ自動制御、Live Core、Remote を変更しません。
Lift Trace の単独実行、開始から最大 4 分までを保存するルール、
次のプレイ開始時に未保存の映像を破棄するルールも維持されます。
この試作モジュールは通常のアプリ配布には含まれません。

録画による比較と検証範囲は[測定結果](RESULTS.md)を参照してください。

ソースは `lift_trace_native_pacing` という OBS ソースを登録します。
試験する OBS と一致する公式 OBS SDK の `obs-module.h`、`util/platform.h`、
libobs を使い、独立したプラグインとしてビルドします。C11 のアトミック操作を
使用し、C++ やワーカースレッドは必要ありません。
独立したプロファイルとシーンを持つ使い捨ての OBS 環境でのみ読み込んでください。
試験用 DLL を普段使っている OBS のインストール先やリリースパッケージに
コピーしないでください。リポジトリには OBS のヘッダー、ライブラリ、
コンパイル済みバイナリーを含めません。
`CMakeLists.txt` は公式 SDK を使う場合の参考ビルド手順であり、
この環境では実行して検証していません。録画実験では Clang とローカルの
最小 ABI ヘッダーを使用しました。そのヘッダーとローカルのツールチェーンは
本実験の公開ソースには含まれません。

## 実装範囲

- 合成された鍵盤入力だけを描画します。インデックス -3 から 120ms ごとに押し、
  レーン `positiveMod(index, 7) + 1` で 40ms 保持します。
  コントローラーへのアクセス、スクラッチの実装、実入力の受信、
  設定 UI とのリアルタイム連携はありません。
- 既存の正規化済み設定を、`lift_settings` という OBS データオブジェクトとして
  渡せます。これは試験ツールが渡す設定スナップショットであり、別途管理する
  ユーザー設定ファイルではありません。将来の連携では既存 UI から同じ設定を
  送る構成にできますが、今回の実験ではその連携を実装していません。
- `video_tick` で OBS の映像フレーム時刻と設定スナップショットを取得します。
  独立して動くブラウザーのアニメーション時計ではなく、このスナップショットで
  描画します。設定更新は短いロックで保護し、ロック中には入出力や
  グラフィックス API を呼びません。時計が 0 または逆行した場合も、
  経過時間が負にならないよう処理します。
- レーン比率、移動速度の計算、表示遅延、先端のみ／本体も表示する切り替え、
  終了した短い入力の表示ルールは既存の計算に従います。
  表示オプションによって入力タイムスタンプを変更しません。
  非常に遅い速度に設定しても、ブラウザーエンジンと同じ 4,096 イベントの上限で
  処理量を制限します。
- 位置・サイズ・時間計算の一致を確認する実験です。
  Canvas の輪郭アンチエイリアス、色処理、スクラッチ表示、
  すべての OBS モードでの透明度が完全に一致することは保証しません。

既定値は入力ノーツ領域 432 × 290px、その下の診断領域 100px、
先端の厚さ 12px、速度 849.9266666666666px/s です。
7 つの鍵盤レーンを使い、スクラッチはレーンの幅だけを確保します。
同じ条件で比較するには、432 × 390、60fps、拡大縮小なし、
不透明な背景を使用してください。診断バーコードには最低 336px の幅が必要です。
それ以外の正規化済みの幅は、今回のフレーム周期比較の検証範囲に含みません。

## 診断値と解釈

24 ビットの行を 5 つ使い、各セルは 10 × 14px です。
`x = 8 + bit * 12` の位置に最下位ビットから並べます。
既定の高さでは、各行の上端は 300、318、336、354、372 です。
各行の x=308 と x=324 に白・黒の校正用長方形を配置します。

| 行 | ネイティブ描画の値 |
| --- | --- |
| 1 | OBS の映像 tick の連番 |
| 2 | OBS アニメーションの経過時間、0.1ms 単位 |
| 3 | tick コールバックの OS 経過時間、0.1ms 単位 |
| 4 | アニメーションの経過時間、0.1ms 単位で 2 行目と同じ |
| 5 | 前回の描画コールバックの CPU 実行時間、µs 単位 |

2 行目は初期化された最初の OBS 映像 tick で、3 行目は最初のコールバックで
0 になります。この試験で想定するように最初の tick から有効な OBS 時刻が
得られれば、両者の起点は一致します。最初の OBS 時刻が 0 の場合は 2 行目の
起点が遅れるため、その差は絶対的な時計の位相差の測定値ではありません。
描画時間には GPU 処理の完了や映像エンコードを含みません。
複数の描画呼び出しが同じ tick を使うことは正常な場合もあるため、
カウンターだけでなく、独立して測定したピクセル移動と出力 PTS も確認する
必要があります。小規模な合成比較の成功だけでは、実プレイの動作や
OBS/GPU の過負荷時の安定性まで実証できません。

## 位置・サイズ計算の回帰検査

`geometry-test.c` を別の共有ライブラリとしてビルドします。
OBS には依存せず、`pacing_geometry_tests` と `pacing_geometry_sample` を
エクスポートします。次のように実行します。

```text
python check-geometry.py path/to/geometry-test.dll --node path/to/node
```

時計の開始・逆行、処理量の上限、および実際の `web/engine.js` と
`web/render.js` を呼び出して生成した 420 個の比較ベクトルを検査します。
先端のみ／本体も表示する場合、短い入力の表示比率と厳密な基準時間の境界、
表示遅延、1P/2P 配置、押す前・保持中・離した後・除去済みの状態、
元のタイムスタンプの保持を確認します。
検査は OBS プロセスを起動せず、個人設定にもアクセスしません。
