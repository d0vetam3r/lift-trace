# OBS ネイティブ描画のフレーム周期実験

[한국어](README.ko.md) · [日本語](README.ja.md) · [English](README.md)

これは任意で使用する描画実験であり、**正式配布された代替オーバーレイではありません**。
OBS が映像を合成する際に入力ノーツを直接描くことで、ブラウザーソースで
観測された同一フレームの繰り返しと、その後の急な移動を避けられるか確認します。
これらのファイルは、既存の Lift Trace 実行ファイル、設定 UI、実入力の記録、
オーバーレイ自動制御、Live Core、Remote を変更しません。
Lift Trace の単独実行、開始から最大 4 分までを保存するルール、
次のプレイ開始時に未保存の映像を破棄するルールも維持されます。
この試作モジュールは通常のアプリ配布には含まれません。

録画による比較と検証範囲は[測定結果](RESULTS.md)を参照してください。

ソースは `lift_trace_native_pacing` という OBS ソースを登録します。
試験する OBS と一致する公式 OBS SDK の `obs-module.h`、`util/platform.h`、
libobs を使い、独立したプラグインとしてビルドします。C11 のアトミック操作を
使用します。C++ は不要で、Windows の接続処理は小さな別スレッドが担当します。
接続ハンドルは OBS の映像スレッドの外で開きます。
独立したプロファイルとシーンを持つ使い捨ての OBS 環境でのみ読み込んでください。
試験用 DLL を普段使っている OBS のインストール先やリリースパッケージに
コピーしないでください。リポジトリには OBS のヘッダー、ライブラリ、
コンパイル済みバイナリーを含めません。
`CMakeLists.txt` は公式 SDK を使う場合の参考ビルド手順であり、
この環境では実行して検証していません。録画実験では Clang とローカルの
最小 ABI ヘッダーを使用しました。そのヘッダーとローカルのツールチェーンは
本実験の公開ソースには含まれません。

## 実入力と既存の設定 UI (Windows)

試験用ランチャーは既存の `Bridge.subscribe()` を購読します。所有する Node
プロセスで、変更していない `web/client.js` の `InputClient`、`TrailEngine`、
`ScratchTracker` を使用します。既存 UI の機器選択、ボタン割当、スクラッチの
軸・反転・感度・停止猶予、設定更新とリセットを同じ経路で受信します。
元の入力記録へ変更を書き戻しません。

```text
python experiments/obs-native-pacing/live_launcher.py --node PATH_TO_NODE_EXE --channel lift-test
```

実験には Python 3.10+、Node 22+、別途ビルドしたプラグインが必要です。
通常の Lift Trace は Node・プラグイン・Live Core・Remote なしで単独実行できます。
既存 UI は `http://127.0.0.1:8766/`、既定の設定保存先は分離された
`artifacts/native-live-data` です。そこで機器を選び、既存の設定項目を使います。
コピーした設定は既存のインポート機能で読み込めます。C 専用の設定ファイルは
不要です。同じ設定フォルダーを二つのランチャーから同時に使用しないでください。
OBS 試験ソースの `Live channel` には同じ `lift-test` を指定します。
接続スレッドは未起動の相手を 100ms ごとに再試行するため、起動順は問いません。
実入力モードの診断領域は既定で無効です。

Windows セッション内の共有メモリーで最大 4,096 個の入力区間を渡します。
OBS はロックを待たず、自身の映像フレーム時計で描画します。接続停止や不正な
データでは 1 秒以内に入力ノーツを消去し、既存の入力ポーリングと UI は続行します。
観測側は 4ms 間隔でスクラッチ停止を判定するため、60Hz ブラウザーより約 1 フレーム
早く猶予の終了を観測する場合があります。生のサンプル時刻と猶予の規則は維持します。

先端／本体、短い入力の表示率、遅延、1P/2P、寸法、速度、ガイド、背景は既存 UI の
設定に従います。スクラッチは鍵盤の表示設定に関係なく本体と方向の色・矢印を保ちます。
任意の自動配置・表示の接続は以下で説明します。ランチャーは既存のソースや録画対象を自動移行しません。
実際のプレイと入力遅延は別途確認が必要です。自動入力の試験は実機検証ではありません。

## 実装範囲

### 実行中のLift Traceアプリへの接続

既存アプリが入力サーバーを実行している場合は、別の `live_launcher.py` を起動せず、
`live_observer.py --node PATH_TO_NODE_EXE --channel lift-test --port 8765` を使います。
この任意の観測プロセスは既存のローカル状態・イベントストリームだけを読みます。
入力ポーリング・UI・自動表示・録画を重複起動せず、アプリ設定を書き込みません。
切断や不正なストリームではスナップショットを無効にし、自身のNodeを終了した後、
新しいエンジンでサーバーの現在状態を取得して再接続します。

OBSと一緒に起動する場合は `obs-native-observer.lua` を追加し、Python・Nodeのパス、
既存Lift Traceのポートとチャンネルを設定して任意の自動起動を有効にします。
管理者権限を要求せず非表示で起動し、OBSの正確なプロセス作成時刻を確認します。
そのOBSの終了時に観測プロセスと子プロセスも終了します。既存アプリ・ヘルパーは
自身のサーバーと自動表示を引き続き管理します。Lift TraceやRemoteのポートで別の
サーバーを起動しないでください。任意の状態JSONは接続・寿命の情報だけを記録し、
実入力や設定を含みません。スクリプト削除・再読み込みで推測したPIDを終了することはなく、
最初に接続したOBSの寿命に従います。

### 任意のOBS自動配置と自動表示

分離したOBSに `obs-native-layout.lua` をスクリプトとして追加します。
ランチャーと同じチャンネルと別のソース名を指定し、対象シーンで追加・接続ボタンを
使います。新しい項目は非表示で作成し、既存項目の表示状態は維持します。
ボタンは標準配置のため倍率・クロップ・回転・配置基準・境界設定を初期化します。
その後の設定追従はX/Yだけを変更し、表示状態・順序・ロック・その他の変換を保ちます。
手動で位置を管理する場合は追従を無効にします。

既存UIの1P/2P、LIFT、`obsOffsetX/Y`を使い、`getObsPlacement`と同じ1920×1080の
基準で計算します。出力寸法は既存の描画設定に従います。配置タイマーは小さな
共有メモリーヘッダーだけをロック待機なしで読み、ファイル読み込み・ソケット要求・
ハンドル取得を繰り返しません。データが未取得・古い・不正な場合は最後の位置を維持します。
起動順は問わず、同じチャンネルの送信プロセスを再起動しても表示状態は変えません。

シーンUUID・項目ID・ソースUUID・チャンネルを固定して保存します。改名しても
接続を維持し、シーン切り替えで別項目を追従しません。ソース・項目の置換や
チャンネル変更には明示的な再接続が必要です。重複配置は正確な項目がすでに固定
されている場合だけ許可し、同名のブラウザーソースを置換しません。配置補正値を
送るプロトコルv2を使うため、ランチャーと一緒に試験プラグインも再ビルドしてください。
v1データは旧予約領域を位置として誤読しないよう拒否します。

自動表示はランチャーの**既存の自動制御UI**で分離したOBSに接続し、ゲームの
キャプチャーとCオーバーレイ項目を選択・保存して開始します。既存の検出・確定待ち・
キャプチャー復旧の方針をそのまま使います。配置機能が自動表示を開始したり既存項目を
表示・非表示にしたりすることはありません。ソース実行での任意の自動表示依存関係は
[開発ガイド](../../docs/DEVELOPMENT.ja.md)を参照してください。

Live Coreは任意の連携先であり変更していません。後で録画を移行する際にはCoreでも
新しいC項目の識別子を明示的に選択します。ソースの作成・改名だけで既存の録画対象は
変わりません。開始から最大240秒の保持と次のプレイでの未保存映像の破棄はCoreが
維持します。今回の変更は通常の配信環境へのインストールや設定変更を行いません。

- 実入力チャンネルが空の場合は合成鍵盤入力を描画します。インデックス -3 から 120ms ごとに押し、
  レーン `positiveMod(index, 7) + 1` で 40ms 保持します。
  この比較モードは機器を読みません。実入力には上記の任意の観測プロセスを使います。
- 既存の正規化済み設定を、`lift_settings` という OBS データオブジェクトとして
  渡せます。これは試験ツールが渡す設定スナップショットであり、別途管理する
  ユーザー設定ファイルではありません。実入力モードは既存 UI の正規化済み設定を受信します。
- `video_tick` で OBS の映像フレーム時刻と設定スナップショットを取得します。
  独立して動くブラウザーのアニメーション時計ではなく、このスナップショットで
  描画します。設定更新は短いロックで保護し、ファイル・パイプ入出力と
  グラフィックス API は外側で実行します。共有メモリーのロックは待ちません。合成時計が 0 または逆行した場合も、
  経過時間が負にならないよう処理します。
- レーン比率、移動速度の計算、表示遅延、先端のみ／本体も表示する切り替え、
  終了した短い入力の表示ルールは既存の計算に従います。
  表示オプションによって入力タイムスタンプを変更しません。
  非常に遅い速度に設定しても、ブラウザーエンジンと同じ 4,096 イベントの上限で
  処理量を制限します。
- 位置・サイズ・時間計算の一致を確認する実験です。
  Canvas の輪郭アンチエイリアス、色処理、スクラッチ表示、
  すべての OBS モードでの透明度が完全に一致することは保証しません。

既定値は入力ノーツ領域 432 × 290px、その下の診断領域 100px、
先端の厚さ 12px、速度 849.9266666666666px/s です。
合成比較モードは 7 つの鍵盤レーンを使い、スクラッチはレーンの幅だけを確保します。
同じ条件で比較するには、432 × 390、60fps、拡大縮小なし、
不透明な背景を使用してください。診断バーコードには最低 336px の幅が必要です。
それ以外の正規化済みの幅は、今回のフレーム周期比較の検証範囲に含みません。

## 診断値と解釈

24 ビットの行を 5 つ使い、各セルは 10 × 14px です。
`x = 8 + bit * 12` の位置に最下位ビットから並べます。
既定の高さでは、各行の上端は 300、318、336、354、372 です。
各行の x=308 と x=324 に白・黒の校正用長方形を配置します。

| 行 | ネイティブ描画の値 |
| --- | --- |
| 1 | OBS の映像 tick の連番 |
| 2 | OBS アニメーションの経過時間、0.1ms 単位 |
| 3 | tick コールバックの OS 経過時間、0.1ms 単位 |
| 4 | 合成: 2行目と同じ。実入力: UTC アニメーション ms × 10 を24ビットで循環 |
| 5 | 前回の描画コールバックの CPU 実行時間、µs 単位 |

2 行目は初期化された最初の OBS 映像 tick で、3 行目は最初のコールバックで
0 になります。この試験で想定するように最初の tick から有効な OBS 時刻が
得られれば、両者の起点は一致します。最初の OBS 時刻が 0 の場合は 2 行目の
起点が遅れるため、その差は絶対的な時計の位相差の測定値ではありません。
描画時間には GPU 処理の完了や映像エンコードを含みません。
複数の描画呼び出しが同じ tick を使うことは正常な場合もあるため、
カウンターだけでなく、独立して測定したピクセル移動と出力 PTS も確認する
必要があります。小規模な合成比較の成功だけでは、実プレイの動作や
OBS/GPU の過負荷時の安定性まで実証できません。

## 位置・サイズ計算の回帰検査

`geometry-test.c` を別の共有ライブラリとしてビルドします。
OBS には依存せず、`pacing_geometry_tests` と `pacing_geometry_sample` を
エクスポートします。次のように実行します。

```text
python check-geometry.py path/to/geometry-test.dll --node path/to/node
```

時計の開始・逆行、処理量の上限、および実際の `web/engine.js` と
`web/render.js` を呼び出して生成した 420 個の比較ベクトルを検査します。
先端のみ／本体も表示する場合、短い入力の表示比率と厳密な基準時間の境界、
表示遅延、1P/2P 配置、押す前・保持中・離した後・除去済みの状態、
元のタイムスタンプの保持を確認します。
検査は OBS プロセスを起動せず、個人設定にもアクセスしません。
