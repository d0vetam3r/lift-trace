# リリース手順

[한국어](RELEASING.md) · [日本語](RELEASING.ja.md) · [English](RELEASING.en.md)

[開発ガイド](DEVELOPMENT.ja.md) · [検証状況](VALIDATION.ja.md) · [変更履歴](../CHANGELOG.ja.md)

同じソースコードから、**そのまま実行できるWindowsアプリ**と、**そのアプリの作成に使ったソースZIP**を配布します。個人の作業フォルダーをコピーするのではなく、リリース対象のソースを確定してから二つのファイルを作成します。

## 担当と役割

| 担当 | 役割 |
| --- | --- |
| 貢献者 | 一つの目的に絞って変更し、関連チェックを実行して未確認の点を説明します。作業ブランチを使い、`main` にPRを出します。[ブランチとレビュー](../CONTRIBUTING.ja.md#ブランチとレビュー)を参照してください。 |
| 管理者 | 変更をレビューし、バージョンと正確なコミットを決めます。実際の使用結果とリリースノートを確認し、公開を承認します。 |
| GitHub Actions | 設定済みのテストとビルドを実行し、ハッシュを計算して生成ファイルを保存します。成功表示はそのチェックを通過したことを示し、公開の可否を判断するものではありません。 |
| AIアシスタント | 管理者の許可した範囲で変更、ツールの実行、説明の作成を支援します。確認結果と未確認事項を正確に区別し、人のレビューや実機テストの代わりにはしません。 |

許可されたツールやワークフローでリリースを作成できるため、毎回人がすべてのファイルを手作業でアップロードする必要はありません。何を公開するかは管理者が決めます。現在のワークフローは、以下に説明するビルド成果物の保存までを自動化しています。

## バージョンを準備する

1. PRごとにバージョンを変更せず、リリース準備時に次のバージョンを決めます。`package.json` と画面のバージョン表示を更新し、変更履歴の未リリースから今回の変更を日付付きのバージョン項目へ移します。ユーザー向けのダウンロード手順では、特定のバージョン番号ではなく共通のファイル名の先頭部分を使います。
2. `tools/build_release.py` の配布対象ファイル一覧を確認します。実行に必要なファイル、公開文書、テスト、ビルドツールを含め、ローカル設定、ログ、録画、OBSプロファイル、別の連携機能、個人のパスは除きます。
3. [開発ガイド](DEVELOPMENT.ja.md)のコマンドと、変更に必要な動作確認を実行します。[検証状況](VALIDATION.ja.md)に確認したビルド、結果、残る項目を記録します。Windows・OBSのバージョンやコントローラーは、実際にテストしたものだけを記載します。対応を目指す環境を検証済みとしたり、AIの確認を人のレビューとしたりしないでください。
4. 変更をすべてコミットした同じソースから、ソースZIPとWindows ZIPを作ります。専用のビルド環境で、バージョンを固定した `requirements-build.txt` を使います。

ビルド前に最終的なバージョン、文書、コードをコミットします。検証したそのコミットに、`v0.1.0` のような `vX.Y.Z` 形式のタグを付けます。タグ、`package.json`、ソースZIP、Windows配布版は同じコードとバージョンを指している必要があります。コミットとビルドの実行記録を残し、新しいソースZIPに古い実行ファイルを組み合わせないでください。

公開済みリリースのタグを別のコミットへ移動したり、ZIPやチェックサムを別のビルドで上書きしたりしません。修正は新しいバージョンとして配布します。ファイルを差し替えずに説明を補足することはできます。将来タグ保護ルールでこの運用を強制できますが、現在のワークフローには設定していません。

## ビルドと確認

Windows x64で、未コミットの変更や既存の `.venv-build` がないチェックアウトから始めます。準備には利用可能なPython 3.10以降を使い、Windows配布版はバージョンを固定した公式の **Python 3.13.16 x64** で作成します。

```powershell
python tools/prepare_runtime.py
artifacts\python-runtime\python\python.exe -m venv .venv-build
.venv-build\Scripts\python -m pip install -r requirements-build.txt
.venv-build\Scripts\python tools\build_windows.py --require-verified-runtime
python tools/build_release.py
python tools/smoke_windows.py
```

WindowsのビルドにはPyInstallerを使います。これは配布担当者向けのツールであり、一般ユーザーにインストールを求めるものではありません。ソースZIPはPyInstallerなしでも作成できます。`tools/smoke_windows.py` にはWindows ZIPのパスを指定できます。省略した場合は `artifacts/` 内の現在のバージョンを検査します。

準備コマンドは、ダウンロードしたアーカイブ、Windowsマニフェスト、SPDX SBOMを `artifacts/python-runtime/downloads/` に保存し、隣の `python/` フォルダーへランタイムを展開します。ビルド中は両方のフォルダーを保持してください。公式ダウンロードURLとハッシュは `tools/python-runtime.json` に固定されています。システム全体へのPythonインストールやPATHの変更は不要です。

ランタイムの出所検証では、公式メタデータを確認し、展開したファイルを指定の公式アーカイブと比較したうえで、配布版のDLL/PYDも元のファイルと比較します。公式配布物から取得したファイルかを追跡する検査です。公式配布物をソースから再ビルドするものでも、セキュリティ、法的適合性、アプリの品質を認証するものでもありません。

この公式ランタイムを使ったWindowsビルドが検査を通過した記録は[検証状況](VALIDATION.ja.md)にあります。リリースごとに再確認してください。別のランタイムによる通常ビルドは、成功しても `bundledRuntime.runtimeProvenanceVerified: false` になる場合があります。これを出所検証の成功として扱わないでください。ソースZIPにはランタイムを含めません。

配布するファイルは次のとおりです。`<version>` は `package.json` のバージョンです。

- `lift-trace-windows-x64-<version>.zip` — 展開してLiftTrace.exeを実行するユーザー向けアプリ
- `lift-trace-source-<version>.zip` — ソース、テスト、文書、ビルドツール
- `SHA256SUMS` — 同じバージョンの二つのZIPのハッシュ。ファイル別の `.sha256` も添付できます。

アップロード前にWindows ZIPを新しいフォルダーへ展開し、次の項目を確認します。

- システムのPythonやNode.jsがPATHになくてもLiftTrace.exeが起動し、`_internal` フォルダーがすべて含まれています。
- 小さな管理ウィンドウから韓国語・日本語・英語の設定画面を開けます。終了ボタンやウィンドウを閉じる操作で、そのウィンドウが起動したサーバーが終了します。
- 先に動いていた正常なサーバーは再利用し、終了させません。同じアドレスで別のプログラムが動いている場合は、分かる形でエラーを表示します。
- コントローラー設定、キャンセル、デモが動作します。時計回り・反時計回りの手順で逆方向を区別し、軸の値が増える方向がどちらでも、円形の矢印と淡い・濃いコーラル色が正しく表示されます。
- LIFTによる高さの自動計算、手動の高さの維持、以前の設定の読み込み、LIFT 0の案内が動作します。デモの入力ノーツを確認する前にゲームの数値か手動の高さを設定します。アプリのサイズ変更によってOBSのサイズも変わったかのように案内してはいけません。
- 1080pレーンサイズ、X/Y計算、コピーボタン、位置調整値の保存が3言語で動作します。ガイドの左上・100%の配置、従来の手動位置の維持、明示的なOBSへの適用を確認します。アプリの設定を変更するだけでOBSのシーン項目が移動してはいけません。
- OBS連携が同じフォルダーのLiftTrace.exeを見つけてサーバーを起動し、そのOBSプロセスの終了時に自分が起動したサーバーも終了します。再利用したサーバーは動作を続けます。
- 展開したフォルダーで文書内のリンクと説明図を開けます。
- `LICENSE`、`THIRD_PARTY_NOTICES.md`、`licenses/` が含まれています。MITはプロジェクトのコードに適用され、ランタイムの各構成要素にはそれぞれのライセンスが適用されます。
- ランタイムのライセンス告知の出典が実際の構成要素と一致し、`bundledRuntime.runtimeProvenanceVerified` がtrueで、`unverifiedComponents` が空です。記録されたアーカイブ・メタデータのハッシュと配布バイナリの対応一覧を確認し、`provenance/python-runtime.spdx.json` を保持します。ライセンスファイルを含めるだけでは検査は完了しません。
- どちらのZIPにも `data/`、ローカルの認証情報、キャプチャ、個人設定が含まれていません。

自動スモークテストは、画面を開かないパッケージ済みサーバーと、テスト用の親プロセスを使ったOBS起動ヘルパーの終了管理を確認します。デスクトップ画面、実際のコントローラー、OBSでの描画、ゲームキャプチャとのタイミングを直接確かめるテストとは区別してください。

`bundledRuntime.runtimeProvenanceVerified` が示すのは、ビルドツールによる配布元とファイルの整合性の検査だけです。アプリの品質、セキュリティ、法的適合性、ユーザーのPCとの互換性を認証する値ではありません。ほかの確認項目や制約は別に記録してください。

## GitHubワークフローと公開

現在の `.github/workflows/verify.yml` には二つの実行経路があります。

- **pushまたはPR：** WindowsとUbuntuでPython・JavaScriptテストを実行し、ソースZIPを作ります。記録済みの2026-10-12のpush実行では、4通りのテストの組み合わせがすべて成功しました。コミットと実行リンクは[検証状況](VALIDATION.ja.md)にあります。
- **手動のRun workflow：** 上記のテスト後に、公式ランタイムの準備、`--require-verified-runtime` によるWindowsビルド、スモークテストを実行し、ZIPとハッシュをActionsの成果物として保存します。記録済みのpush実行ではWindowsビルドのジョブをスキップしたため、その実行でEXEを作ったことにはなりません。

このワークフローの権限は `contents: read` です。**リリースの下書きを作成したり、GitHub Releaseを公開したりはしません。** Actionsの成果物はその実行に保存したビルド結果であり、Releasesのダウンロードとは別です。

公開時は検証済みのソースを選び、バージョンタグとGitHub Releaseの下書きを作成します。二つのZIPとチェックサムをリリースの **Assets** に追加します。説明ではWindows ZIPを先に案内し、**Windowsアプリ — Pythonのインストール不要** と表示します。ソースZIPは **貢献者向けソース** として区別します。

リリースノートには、実際に確認した環境、既知の制約、コード署名の有無を記載します。検証記録へのリンクを付け、未完了の確認は保留のまま残します。現在のアプリは **コード署名のない初期の試作版** です。署名済みと説明したり、Windowsやウイルス対策ソフトの保護機能を無効にするよう案内したりしないでください。チェックサムだけで配布者の身元を証明できるわけでもありません。将来署名を追加する場合は、最終アーカイブのハッシュを生成する前に署名し、文書も更新します。

下書きのファイル、リンク、説明を確認してから公開します。3言語のREADMEのダウンロードリンクは最新リリースを指すように維持します。ユーザーの導入先として、GitHubが自動生成したソースアーカイブだけを提供しないでください。

## 今後検討する自動化：リリースの下書き作成

**以下は提案であり、まだ設定していません。** 管理者が信頼できるコミットとバージョンを選ぶ → Actionsがそのコードをチェック・ビルドしてハッシュを計算する → 結果をリリースの下書きに添付する → 管理者が実際の使用結果、説明、ファイルを確認して公開を承認する、という流れです。自動処理の成功から機器の互換性、タイミングの精度、文章の自然さまで確認できたと判断してはいけません。未確認事項はリリースノートに残します。

実装する場合、テスト・ビルドのジョブは読み取り権限のままにし、下書き作成とファイル添付のジョブだけに `contents: write` を付与します。リポジトリに組み込まれた `GITHUB_TOKEN` を使い、この設計に個人アクセストークン（PAT）は不要です。GitHubの[権限設定](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)と[ジョブごとのトークン権限](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token#modifying-the-permissions-for-the-github_token)を参照してください。

リリースのジョブは、管理者が選んだ信頼できるリポジトリ参照だけで実行します。フォークからのPRのコードをリリース権限で実行したり、そのコードへシークレットを渡したりしないでください。入力はレビュー済みのコミットに結び付け、任意のブランチ名や信頼できないPRが提供した成果物を使わないようにします。GitHubの[フォークワークフローの権限制限](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflows-in-forked-repositories)に従います。

自動化やAI支援はセキュリティ監査や法的な認証にはなりません。ハッシュはファイルの変更を検出できますが、配布者の身元を証明するものではなく、現在のアプリは未署名です。実際のコントローラー、ゲームとOBSのタイミング、各言語の読者によるレビューは別に行い、実際に確認した範囲を[検証状況](VALIDATION.ja.md)へ記録してください。
